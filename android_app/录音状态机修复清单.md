## 直接回答："用户报的'没连接，开始→结束 卡住'是哪条？"

**最可能就是【第 1 组】**——但有一个关键的现实修正：

源码 `startRecordingInternal`（行 192-198）未连接分支里 **根本没有 `applyState`**，只设了 `pending*` 标志就 `openScan()` return。所以严格走"没连接 → 点开始 → 点结束"这条路时，**网页按钮从头到尾都是 enabled 的"开始"态，永远走不到 `stopRecordingInternal`**，"再点结束"实际是"再点一次开始"。用户主观体验是"卡住了"（反复弹扫描页 / 按钮点了没反应 / 在 idle 和扫描页之间打转，永远进不了录音、也结束不了），**但底层不是按钮 disabled 卡死，而是"意图静默丢失 + 无任何反馈"**。

真正会让按钮**永久 disabled 卡死**的，是【第 2 组】（断开后状态残留 → 重连点开始被 `startRecording` 守卫静默吞掉，网页永停 `starting`）和【第 3 组】（假连接 starting 5s 锁）。这两条与用户的"没连接"描述也高度吻合（半连接 / 假连接 / 连上即闪断）。

**结论：先修第 1 组（最贴合字面复现），第 2、3 组紧随（同类"卡 disabled"且场景重叠）。** 三者建议作为一个补丁一起上。

## DATA-LOSS（中优先，连录/慢网下）

### 第 7 组 同段被下载/上传两次 → 后端落两条 recording
*(原 queue#2)*

- **一句话问题**：`processAndUpload` 在 worker 线程长耗时（解码/上传）期间不受 `pauseWorker` 管，中途笔开/停录触发 `kickWorker` 再 `peek` 到尚未 remove 的 taskA → 同段被处理两次，`workerTaskDone` 回调两次、`remove` 两次、`onPenUploaded` 两次。
- **精确触发**：taskA 进 `processAndUpload`（慢网未 remove）→ 笔录第2段 `pauseWorker` 清 `workerBusy` → 结束 `kickWorker`（行 491）三闸全过 → `peek` 仍是 taskA → 二次 `processAndUpload(taskA)`。
- **最小安全修法**：加 `private volatile UploadTask inflightTask = null;`
  - `onFileDownloadComplete`（行 381）交 worker 前 `inflightTask = task;`
  - `kickWorker`（行 495）peek 后 `if (task == inflightTask) { notifyPending(); return; }`
  - `pauseWorker`（行 507）开头 `if (inflightTask != null) return;`（已进上传阶段不占蓝牙、不打断）
  - `workerTaskDone`/`workerTaskFailed` 末尾 `inflightTask = null;`

### [conn/stuck] 录音中途断开(走远)后, penRecording/sessionActive 永不复位 → 网页永久卡"录音中", 且会污染下一段

- 触发: 1) 录音笔已连接并在录：App 点开始→笔回 onRecordStateChanged(true)（PenController:308-325），penRecording=true、sessionActive=true、RecordingBus=STATE_RECORDING，网页 __appRecording=true、按钮显示"结束录音"、计时器在跑。2) 人走远/蓝牙掉线，SDK 回 onDisconnected(device,reason)（443）。3) onDisconnected 只刷连接点，不 post 任何录音状态；SDK 不会再补 onRecordStateChanged(false)。4) 用户【不去点结束】（很常见：以为还在录）。→ 网页永久停在"录音中/陪伴进行中"，计时器持续空跑，无任何自动回 idle/error。即使切到别的页再回接诊页，onResume 用 RecordingBus.lastState=recording 再次确认"录音中"。（补充：若用户此时去点"结束"，约 4s 后由 stopRecording 的 4s 兜底 finishSessionEnqueue 回 idle 并清标志，可恢复——所以"卡死下一段"仅在用户始终不点结束时残留。）
- 修法: 在 PenController.onDisconnected 里，断开时若本段仍在跟踪，就把它当异常结束收回到 idle/error，复用现有 finishSessionEnqueue / sessionGen / post 机制：

```java
@Override
public void onDisconnected(AIRECBleDevice device, String reason) {
    if (listener != null) main.post(() -> listener.onPenConnected(false));
    // ★断开即收尾：否则镜像永久卡在"录音中"，计时空跑、标志位残留。
    if (sessionActive || penRecording || appStartPending) {
        main.removeCallbacks(confirmTimeout);
        penRecording = false;
        appStartPending = false;
        if (sessionActive) {
            // 有文件名就排队补传（重连后再下载），无则纯复位并报错。
            // finishSessionEnqueue 内部会 sessionGen++、复位 sessionActive 等，并 post(STATE_IDLE)。
            finishSessionEnqueue(sessionFileName, elapsedSec(), sessionStartWallMs);
            if (TextUtils.isEmpty(sessionFileName)) {
                // 没文件名时 finishSessionEnqueue 已 post(STATE_IDLE)，这里改成更如实的报错更好：
                post(PhoneMicService.STATE_ERROR, "录音笔已断开，本段可能未保存，请重连后重试", 0, -1);
            }
        } else {
            // 只是 appStartPending（还没真开录就断了）：作废本段并报错。
            sessionGen++;
            sessionStartWallMs = 0;
            post(PhoneMicService.STATE_ERROR, "录音笔已断开，请重连后重试", 0, -1);
        }
    }
    if (workerBusy && currentTask != null) {
        workerTaskFailed(currentTask, "disconnected", false);
    }
}
```

要点：(a) 必须 removeCallbacks(confirmTimeout)，避免断开+report 后再触发休眠误判；(b) finishSessionEnqueue 已自带 sessionGen++ 与标志复位，能防误伤重连后新开的下一段；(c) post(STATE_ERROR/IDLE) 会经 ConsultantActivity.onStatus → __onNativeRecState 把网页按钮 enable、停计时、回 idle/error，彻底解卡。无文件名分支用 STATE_ERROR 比 STATE_IDLE("已结束") 更如实，避免把"断开丢失"显示成"已保存"。

### [queue/data-loss] processAndUpload 在自有 worker 线程跑解码/上传期间，penRecording/pauseWorker 改了状态，但这条任务不受 pauseWorker 管，且完成回调用旧 task 直接 remove——与重新入队的同名 task 冲突
